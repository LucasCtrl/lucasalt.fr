Keyboard enthousiast for five years now and happy owner of a BambuLab P1S since spring 2025 I wanted to print a keyboard to combine both of my hobbies.

# Design

## Layout

Printing a full size keyboard in one piece is outside the capabilities of the 3D printer as the maximum printing dimensions are 256x256x256mm but keyboard sizes are not limited to full size keyboard like we know from Corsair, Logitech, ...

Smaller keyboards exists and I enjoy really small keyboards called 40%. They "lack" the numpad, arrow cluster, F row, numrow, ...

It basically a keyboard with only the alphas (letters).

![Anatomy of a keyboard](/img/EK_10/keyboard-anatomy.jpg)

You will say: Great, but can you write with this ? Short anwser, yes.

With a small keyboard, you will only have the possibility to write lowercase letter. So to improve or add new characters without adding new keys, we will use a function called layers.

But what are layers you will ask. Think about the `Shift` key. When you press on the letter `a`, you have a lowercase `a`. By pressing on `Shift + a`, you will go to a layer for uppercase letters and an uppercase `A` will appear on your screen. With a 40% keyboard, you will not only have 1 or 2 layers but 3 or 4 with specific purposes (layer 1 for uppercase letters, layer 2 for symbols, layer 3 for numbers, ...).


Now I know, that I want a 40% keyboard, but which layout. Something identically to a [Minivan](https://40s.wiki/boards/minivan), a [Le Chiffre](https://40s.wiki/boards/le_chiffre), a [QAZ](https://40s.wiki/boards/qaz), ... ? I already own some of them or something apparenting to them, but something that I didn't tried yet is something like a [Planck](https://40s.wiki/boards/planck). An ortholinear keyboard which is 12u[^ft-note1] in length and 4u[^ft-note1] in height.

To simplify the design a make the keyboard even more compact, I'll trim down 2 columns and remove some unwanted keys at the bottom left and bottom right.

Now that I know a bit better where I will go with this, it's time to start sketch and visualize this keyboard on a computer. Some really great tools online exists and make our life easier.

## Design

### 1. KLE

After the keyboard layout defined, I always start with [KLE (Keyboard Layout Editor)](https://www.keyboard-layout-editor.com/). KLE is one of the most popular tool for keyboard enthousiast. It allow us to represent the keyboard from the top with all the keys, their specific size, position as well as the symbols defined under each keys. It's also the backbone of many project related to the keyboard community like the software on each keyboard, some automatic keyboard generators, ...

![Keyboard preview in KLE](/img/EK_10/kle.png)

Now I have my keyboard represented, I'm gonna grab the JSON data generated by KLE to use it "everywhere", ai03 plate generator for the automatic generation of the plate, QMK for the firmware of the keyboard, and for GitHub to populate the documentation about this project.

### 2. ai03 plate generator

After the JSON data grabbed from KLE, on [ai03 plate generator](https://kbplate.ai03.com/), I will be able to automatically generate the plate for my future keyboard. The tool is easy to use, fast and customizable. For example, I always disable the fillet because I like to defined them on the 3D model, I also like to customize my stabilizer orientation with the flags `_rs`. I generally do this to orient the wire of my stabilizer in the keyboard and not having it at the edge of the plate.

```json
[{a:7},"","","","","","","","","",""],
["","","","","","","","","",""],
["","","","","","","","","",""],
[{x:2},"","",{w:2,_rs:180},"","",""]
```

![Plate preview in ai03 plate generator](/img/EK_10/ai03_plate_generator.png)

Then, I can simply download the SVG or DXF file. He can be directly sent to a manufacturer to cut the plate to your needs or import them in a CAD software to edit the plate shape and design the keyboard around.

### 3. OnShape

Finally, the part where I'm like a fish in the water, one of my favorite part : CAD[^ft-note2]. I will now define the global shape of the keyboard. Until now, the only defined thing was the placement of the keys on my future keyboard. For this part of the process, many tools are available, free ones ([FreeCAD](https://www.freecad.org/), [OpenSCAD](https://openscad.org/), ...), freemium ones ([Fusion 360](https://www.autodesk.com/products/fusion-360/), [OnShape](https://www.onshape.com/), ...) and professional ones ([SolidWorks](https://www.solidworks.com/), [Creo](https://www.ptc.com/en/products/creo), ...). As a CAD[^ft-note2] and CAM[^ft-note3] trainer, I work with professional software every day but I don't want to spend a lot of money in the keyboard hobby especially for a CAD software. In that case, I prefere to look at free or freemium alternatives. Over the years, I tend to stick with OnShape who is more or less identical to Creo philosophy.

The first thing I like to do, even before sketching the case, is to define variables. Those variables will be very handy during the design process. The main purpose of the variables is to replace a dimension by a name, this name is then linked to a variable. If you use this variable across multiple drawings, features or files, by changing the variable value, the dimension will be changed everywhere. You can compare this to a formula in Excel, you have the possibility to use a cell value in a formula to calculate something. If a value change, you don't need to change the formula itself, just the value in the cell which was refered.

![Project variable list](/img/EK_10/variable_list.png)

After that, I tend to create a file per part, and regroup everything into sub-assemblies and assemblies. It can be complicated at first, because you need to maintain multiple files for the whole design but it approach the reality, you assemble (assembly file) multiple parts (part file) together.

![Project tree view in OnShape](/img/EK_10/onshape_tree.png)

![Assembled view](/img/EK_10/EK_10_compact.png)

![Exploded view](/img/EK_10/EK_10_exploded.png)

Once convinced by the result of the project, I exported all the parts as `.3mf` files to be able to import them in Bambu Studio to 3D print them.

## 3D Printing

With a printer from BambuLab, the setup process is pretty straight foward. I imported each component on their own plate and defined some parameters that I really wanted to change. But if you don't really care about the specific setting, you just have to import the file and press print.

By default, a slicer[^ft-note4], the app that convert the 3D model to something understable by the printer, create an empty model. If you print the part, you will only have an empty shell and the part will not be very solid. To avoid this, parts are generally printed with a 10-20% infill to create a "scaffold" and reinforce the structure of the part. The benefit of printing a part with a low percentage of infill is that the printer will use less material and will be quicker to print the part, the downside is that the print will sound hollow. In keyboard design, we tent to avoid hollow sound, that why, the keyboard will be printed with a 100% infill at cost of material and printing time.

To print the part, the printer will melt plastic and deposit it on a plate via an extruder[^ft-note5]. To reach the desired part height, the extruder[^ft-note5] will deposit melted plastic on top of already extruded plastic, layer by layer. With the extruder[^ft-note5] installed on my printer, BambuLab suggest me to print layers between 0.12 and 0.28mm. If I print with a 0.12mm layer height, the print time will be longer than a 0.28mm. However, I will be able to print the part with a better resolution. In my case, my parts are not very detailed so I go with a 0.28mm layer height. With this choice, I managed to reduce the time by more than 50% !

```
Case height: 20 mm
Time per layer: around 3 min

With a 0.12mm layer height:
20 / 0.12 = 166.667 lets round it to 167 layers
167 * 3 = 501 min converted in hours, around 8h20

With a 0.28mm layer height
20 / 0.28 = 71.428 lets round it to 72 layers
72 * 3 = 216 min converted in hours, around 3h40
```

Another downside of 3D printing is called the seam. By default, when the printer finished a layer, he will start the next one on top of the starting position of the previous layer. On one or two layer, you dont really see it. For taller part, it create an effect like the seam of you shirt. To avoid this, the slicer[^ft-note4] try to automatically hide this at a corner of the parts. But in some cases, when the part is round or have rounded corner, you can't really hide the seam. To solve this, the seam position can be randomized on each layer and "only" create a teardrop effect where the printer started to print.

![Teardrop effect at the starting position of each layers](/img/EK_10/teardrop_effect.jpg)

The last parameter I setup is a feature called `fuzzy skin`. The printer will deliberatly "vibrate" when he will print the outside of the part. It's allow us to hide deffect like the teardrop mentionned above.

![Fuzzy skin effect](/img/EK_10/fuzzy_skin.jpg)

![Disassembled keyboard](/img/EK_10/disassembled.jpg)

## Problems encountered

### Fuzzy skin in slicer

I the slicing parameters, the fuzzy skin setting were set to only create fuzzy skin at the outside of the part. Sadly, the USB-C opening was creating a path for the fuzzy skin to generate inside the part as well. To solve this issue, I found a small trick in OnShape. As the USB-C was considered as an openning, I took the risk of creating a wall in the 3D model. As so, the slicer will think the part is fully closed and will only generate the fuzzy skin outside. The downside of this is that I will need to post-process the part and remove this fake wall with a exacto knife and a lighter to melt the plastic to smooth out the cuts.

![Left: USB-C cutout - Right: Fake wall to avoid fuzzy skin inside the case](/img/EK_10/fake_wall.png)

### Holes to small

For assembling the keyboard, I had M2 screws laying around. In the CAD model, I drew holes with a diameter of 2mm. The problem with this is that the tolerance of a 3D printer are really big. You can draw a hole with a 2mm inner diameter but have a 1.95 or 1.9mm inner diameter instead. As I printed the case before noticing this issue, instead of reprinting the part with a 2.1 or 2.2mm inner diameter, I simply drilled the holes bigger with a wooden drill bit.

## Assembly

Compared to common products you can find, this keyboard will be handwired. This is a personal challenge, I know how to design a PCB[^ft-note6], but I don't always have the time or the motivation to draw one. Soldering stuff is also a meditation state, you can think and reflect subjects you don't have the time to bother during the week.

A keyboard is not only the wires and the switches, it's also a brain called the controller or MCU[^ft-note7] who will process the electric signals and send the keystrokes to the computer. In my case, I'll use a Pico Mini equiped with a [RP2040](https://www.raspberrypi.com/products/rp2040/). Each keys will be connected to the MCU but the MCU doesn't have enough pad to connect each keys. To solve this, we will use a technic called: matrix circuit. Basically, we will create a grid with columns and rows. Each millisecond, the MCU will scan the grid and detect if a key is pressed. If so, the MCU will get the column and row number and will check which character or keycode he will need to send to the computer.

Creating a matrix is a great way to reduce the pin usage of a MCU but one problem arise: ghosting. I will not enter into the details here but I highly suggest you to read the [QMK documentation about matrix and ghosting](https://docs.qmk.fm/how_a_matrix_works#how-a-keyboard-matrix-works). To solve ghosting I will install 1N4148 diodes in a COL2ROW configuration.

![Wiring diagram of the flipped keyboard](/img/EK_10/wiring.png)

### Preparation

Before soldering components, I started to prepare them. To easily solder the diodes, I winded one of the two legs with [Joe Scotto's diode winder](https://github.com/joe-scotto/scottokeebs/tree/main/Extras/ScottoCoiler). It will create a loop around the switch leg and will simplify the positionning of the diode.

![Diodes before (bottom) and after (top) winding a leg](/img/EK_10/diode.jpg)

Then to have something rigid below the keyboard switches, I used 18 AWG copper wires. Some tend to come with a transparent resin insulator applied which cannot be soldered, so if you would like to do a keyboard yourself, be careful when ordering. To have a cleaner build, I straightened all the wires. I clamped on side of it in a plier or a vice and the other one in a drill. By spinning the drill, the wire straighten itself but also becomes more britles. You need to be very carefull to not over spin the drill otherwise the wire will brake. I then cutted the wires to lenght for the columns and the rows and prepared transparent insulator to insulate the wire between the columns and the rows as the shouldn't touch.

### Soldering

First, I soldered the columns, it's pretty straight forward, but difficult to do. As copper transport heat pretty easily, you need to wait a bit before the solder flow correctly on it. *You will see, on the close up shots, that some joint are not well done due to a lack of heat.*

![Wiring the columns first](/img/EK_10/cols.jpg)

Then the diodes are soldered as well as the wires for the rows. You can also see that on each intersection of column and row, I put transparent insulator to avoid shorts.

![Wiring the rows with the diodes](/img/EK_10/cols_rows.jpg)

To solder the diodes to the rows, I bent the legs around the wire then cut the excess. This ensure the diode is connected correctly to the wire of the rows.

![Close up shot of the diodes before(left) and after(right) cutting the leg](/img/EK_10/diodes_wired.jpg)

After that, the matrix is done. Some flexible wires needs to be soldered on the columns and the rows. After, they are gonna be connected to the MCU.

![Wires from columns and rows to the future MCU](/img/EK_10/cols_rows_wired.jpg)

![Wires connected to the MCU](/img/EK_10/mcu_wired.jpg)

It's then the time to assemble the keyboard completly and close it with some screws.

## Firmware

Usage of [KMK](https://github.com/KMKfw/kmk_firmware), powered by [CircuitPython](https://github.com/adafruit/circuitpython)

Don't need to build hex file. Easily editable on every computer without specific tools.

```python
print("Starting")

import board

from kmk.kmk_keyboard import KMKKeyboard
from kmk.keys import KC
from kmk.scanners import DiodeOrientation

from kmk.modules.holdtap import HoldTap
from kmk.modules.layers import Layers

keyboard = KMKKeyboard()

# Define board pinout
keyboard.col_pins = (board.GP1, board.GP2, board.GP3, board.GP4, board.GP5, board.GP23, board.GP25, board.GP26, board.GP27, board.GP28)
keyboard.row_pins = (board.GP15, board.GP14, board.GP16, board.GP17)
keyboard.diode_orientation = DiodeOrientation.COL2ROW

# Define holdtap
holdtap = HoldTap()
holdtap.prefer_hold = False
holdtap.tap_time = 150

# Append specific modules
keyboard.modules.append(holdtap)
keyboard.modules.append(Layers())

_ = KC.NO

# Home row mods keys
LGUI = KC.HT(KC.A, KC.LGUI)
LALT = KC.HT(KC.R, KC.LALT)
LCTL = KC.HT(KC.S, KC.LCTL)
LSFT = KC.HT(KC.T, KC.LSFT)

RSFT = KC.HT(KC.N, KC.RSFT)
RCTL = KC.HT(KC.E, KC.RCTL)
RALT = KC.HT(KC.I, KC.RALT)
RGUI = KC.HT(KC.O, KC.RGUI)

# Layer keys
LT1 = KC.LT(1, KC.SPC) # Num layer
LT2 = KC.LT(2, KC.TAB) # Nav layer
LT3 = KC.LT(3, KC.BSPC) # Function layer

keyboard.keymap = [
  # Base layer
  [
    KC.Q,    KC.W,    KC.F,    KC.P,    KC.B,    KC.J,    KC.L,    KC.U,    KC.Y,    KC.QUOT,
    LGUI,    LALT,    LCTL,    LSFT,    KC.G,    KC.M,    RSFT,    RCTL,    RALT,    RGUI,
    KC.Z,    KC.X,    KC.C,    KC.D,    KC.V,    KC.K,    KC.H,    KC.COMM, KC.DOT,  KC.SLSH,
    _,       _,       KC.ESC,  LT2,     _,       LT1,     LT3,     KC.ENT,  _,       _
  ],

  # Num layer
  [
    KC.LPRN, KC.N7,   KC.N8,   KC.N9,   KC.RPRN, _,       _,       _,       KC.EQL,  KC.BSLS,
    KC.LBRC, KC.N4,   KC.N5,   KC.N6,   KC.RBRC, _,       KC.RSFT, KC.RCTL, KC.RALT, KC.RGUI,
    KC.GRV,  KC.N1,   KC.N2,   KC.N3,   KC.SCLN, _,       _,       _,       _,       _,
    _,       _,       KC.N0,   KC.MINS, _,       _,       _,       _,       _,       _
  ],

  # Nav layer
  [
    _,       _,       _,       _,       _,       _,       _,       _,       _,       _,
    KC.LGUI, KC.LALT, KC.LCTL, KC.LSFT, _,       _,       KC.LEFT, KC.DOWN, KC.UP,   KC.RGHT,
    _,       _,       _,       _,       _,       _,       KC.HOME, KC.PGDN, KC.PGUP, KC.END,
    _,       _,       _,       _,       _,       _,       _,       _,       _,       _,
  ],

  # Function layer
  [
    KC.F12,  KC.F7,   KC.F8,   KC.F9,   _,       _,       _,       _,       _,       _,
    KC.F11,  KC.F4,   KC.F5,   KC.F6,   _,       _,       KC.RSFT, KC.RCTL, KC.RALT, KC.RGUI,
    KC.F10,  KC.F1,   KC.F2,   KC.F3,   _,       _,       _,       _,       _,       _,
    _,       _,       _,       _,       _,       _,       _,       _,       _,       _
  ],
]

if __name__ == '__main__':
  keyboard.go()
```
